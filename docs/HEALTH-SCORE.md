# Schema Health Score — Algorithm Specification

Version: draft-2
Milestone: M4
Status: Revised — pending implementation approval

## 1. Purpose

The Schema Health score is a deterministic 0–10 indicator that answers
one question for a business owner:

> How complete is the information you've provided for your structured
> data?

It is displayed only in wp-admin, on the plugin's settings page.

## 2. Non-goals

The score is **not**:

- an SEO ranking prediction
- a Google ranking factor or traffic forecast
- a Rich Results eligibility guarantee
- a Google Business Profile score
- a performance metric
- generated by AI or any external service
- an "SEO score" of any kind

The UI must never use language that implies ranking improvement, traffic
gain, or Rich Results eligibility. It measures configuration completeness
— nothing more.

## 3. Constraints

- Deterministic: same settings produce the same score every time.
- No external API calls, no remote requests.
- No telemetry, no tracking, no analytics.
- No new database options or settings keys.
- No changes to the existing 20-key option structure.
- No impact on public JSON-LD generation or frontend performance.
- Computed from the already-loaded settings array only.

## 4. Data inputs

The score uses the existing `local_seo_by_ankit_rawat_options` array
(20 keys).

### Scored keys (15 of 20)

| Key                  | Check it feeds     |
|----------------------|--------------------|
| `schema_enabled`     | Schema output      |
| `business_name`      | Business name      |
| `street_address`     | Core address       |
| `locality`           | Core address       |
| `country`            | Core address       |
| `region`             | Address detail     |
| `postal_code`        | Address detail     |

| `latitude`           | Map coordinates    |
| `longitude`          | Map coordinates    |
| `social_profiles`    | Social profiles    |
| `price_range`        | Price range        |

(15 keys feed 10 checks via groupings.)

### Excluded keys (5 of 20)

| Key                          | Reason excluded                                              |
|------------------------------|--------------------------------------------------------------|

## 5. The 10-point algorithm

Each check is worth exactly 1 point. All checks are independent.

### Check 1 — Schema output enabled (1 pt)

**Condition:** `schema_enabled` is truthy.

**Why this matters:** The fundamental switch. If schema output is
disabled, the structured data is not printed on the site — no search
engine can see it regardless of how complete the business information is.

**When it fails:** The score reflects the missing point. The UI also
shows a separate prominent notice: "Structured data is currently
disabled. Your business information is saved but not visible to search
engines." This notice is independent of the score and always appears when
`schema_enabled` is false.

**Design decision — why not 0/10 when disabled?** A business owner who
has completed all their information but hasn't enabled output should see
that their information is 9/10 complete with a clear single action
remaining (enable output). Zeroing the score would hide completeness and
be discouraging. The score measures configuration quality; the notice
communicates output status.

### Check 2 — Business name (1 pt)

**Condition:** `trim(business_name)` has 2 or more characters.

**Why this matters:** The business name maps to `name` in the JSON-LD.
Without a name, the structured data has no identity. A single character
is almost certainly a typo or placeholder.

**Validation:** `mb_strlen(trim(value)) >= 2`.

### Check 3 — Core address (1 pt)

**Condition:** `street_address`, `locality`, AND `country` are all
non-empty after trimming.

**Why this matters:** These three fields together create the minimum
useful PostalAddress in JSON-LD. The address is the defining feature of
LOCAL business structured data — it tells search engines WHERE the
business is.

- `street_address` → `streetAddress` (specific location)
- `locality` → `addressLocality` (which city)
- `country` → `addressCountry` (which country — disambiguates cities
  with the same name across countries)

All three are universally applicable — every business in every country
has a street, a city/town, and a country. Requiring all three ensures the
address is unambiguous.

**Validation:** All three trimmed strings are non-empty.

**When partially filled:** The recommendation is specific to what's
missing:
- Only street missing: "Add your street address."
- Only city missing: "Add your city or town."
- Only country missing: "Add your country."
- Multiple missing: "Complete your address — add your street, city, and
  country."

### Check 4 — Address detail (1 pt)

**Condition:** At least one of `region` or `postal_code` is non-empty
after trimming.

**Why this matters:** Region (state/province) and postal code add
precision to the PostalAddress. They map to `addressRegion` and
`postalCode` in the JSON-LD, which help search engines distinguish
between businesses in different parts of the same city/country.

The check uses OR — only one is required — because:
- Some countries primarily use states/regions (e.g. US states, Indian
  states, Australian states)
- Some countries primarily use postal codes (e.g. UK postcodes, German
  PLZ)
- Most countries use at least one of the two
- Requiring AND would penalise countries that only use one system

**Fairness note:** In the rare case where a business operates in a
location where neither region nor postal code is applicable, failing this
check costs only 1 point. The score of 9/10 still earns the "Complete"
status label. The check rewards precision where it's achievable without
penalising edge cases into a lower status band.

**Validation:** `trim(region) !== ''` OR `trim(postal_code) !== ''`.

### Check 5 — Phone number (1 pt)

**Condition:** The `phone` value contains at least 7 digit characters
(0–9).

**Why this matters:** Phone maps to `telephone` in the JSON-LD. It's a
primary contact method that search engines display prominently. The
7-digit minimum prevents obviously invalid entries ("123", "test") while
accepting the shortest valid international phone numbers.

**Validation:** Count of characters matching `[0-9]` in the trimmed
string is ≥ 7. Non-digit characters (spaces, dashes, parentheses, `+`)
are ignored in the count.

### Check 6 — Business logo (1 pt)

**Condition:** `trim(logo)` starts with `http://` or `https://`.

**Why this matters:** The logo is the first entry in the JSON-LD `image`
array and is what Google displays in Knowledge Panels. Google recommends
it be at least 112×112px and square. A non-URL value ("foo", "my-logo")
cannot serve as a valid image reference.

**Validation:** Trimmed string matches `^https?://` (case-insensitive).

### Check 7 — Business photos (1 pt)

**Condition:** The `images` array contains at least 1 element whose
trimmed value starts with `http://` or `https://`.

**Why this matters:** Additional images beyond the logo feed the JSON-LD
`image` array. Multiple images give search engines richer visual content
to display. At least one valid URL demonstrates the user has added
meaningful photo content.

**Validation:** At least 1 array element matches `^https?://`
(case-insensitive) after trimming. An empty array, an array of empty
strings, or an array of non-URL strings all fail.

### Check 8 — Map coordinates (1 pt)

**Condition:** Both `latitude` and `longitude` are numeric AND latitude
is in [−90, 90] AND longitude is in [−180, 180].

**Why this matters:** Valid coordinates produce the `GeoCoordinates` node
in JSON-LD, which gives search engines a precise map location. The
JSON-LD builder (`LocalBusiness::geo()`) already requires both values
— if either is empty or invalid, the entire `geo` node is omitted. The
health check mirrors this behavior exactly.

**Validation:**
- Both values pass `is_numeric()`.
- `(float) latitude` is in [−90, 90] (inclusive).
- `(float) longitude` is in [−180, 180] (inclusive).
- If only one coordinate is present, the check fails.

### Check 9 — Social profiles (1 pt)

**Condition:** The `social_profiles` array contains at least 1 element
whose trimmed value starts with `http://` or `https://`.

**Why this matters:** Social profile URLs map to `sameAs` in the JSON-LD,
linking the business entity to its official social media presence
(Facebook, Instagram, LinkedIn, YouTube). This helps search engines
confirm the business identity across platforms.

**Validation:** Same rule as Check 7 applied to the `social_profiles`
array.

### Check 10 — Price range (1 pt)

**Condition:** `trim(price_range)` is not empty.

**Why this matters:** Price range maps to `priceRange` in the JSON-LD.
Google shows it in Knowledge Panels to help customers gauge
affordability. The field accepts freeform values (`$`, `$$`, `$$$`,
`$10-$50`) so even a single symbol is a valid, meaningful entry.

**Why price range and not business type:** Price range is universally
achievable — every business has a price range they can express. Business
type has a valid default (`LocalBusiness`) that cannot be meaningfully
scored (see §12). Price range contributes real data to the JSON-LD that
is absent when the field is empty.

**Validation:** Trimmed string is non-empty.

## 6. Validation summary

| Check            | Rule                                                        |
|------------------|-------------------------------------------------------------|
| Schema output    | Boolean truthy                                              |
| Business name    | `mb_strlen(trim(value)) >= 2`                               |
| Core address     | street_address AND locality AND country all trimmed non-empty|
| Address detail   | region OR postal_code trimmed non-empty                     |
| Phone number     | ≥ 7 digit characters (`[0-9]`) in trimmed value             |
| Business logo    | Trimmed value starts with `http://` or `https://`           |
| Business photos  | ≥ 1 array element starts with `http://` or `https://`       |
| Map coordinates  | Both numeric; lat ∈ [−90, 90]; lng ∈ [−180, 180]           |
| Social profiles  | ≥ 1 array element starts with `http://` or `https://`       |
| Price range      | Trimmed value non-empty                                     |

These are lightweight deterministic checks — not a validation framework.
M7 (inline validation) will add richer field-level feedback.

## 7. Score calculation

```
score = count of passed checks (0–10)
```

No weighting. No multipliers. No bonus points. No dependencies between
checks.

## 8. Status ranges

| Score | Label         | Meaning                                           |
|-------|---------------|---------------------------------------------------|
| 0–2   | Needs setup   | Basic business information has not been entered.   |
| 3–5   | Good start    | Core details are in place; important items remain. |
| 6–8   | Almost there  | Solid setup with a few additions possible.         |
| 9–10  | Complete      | Comprehensive structured data configuration.       |

### Label design rationale

- "Needs setup" — factual, not judgemental. Avoids "Poor."
- "Good start" — encouraging, acknowledges progress. Avoids "Fair."
- "Almost there" — signals proximity to completion.
- "Complete" — factual. 9/10 IS "Complete" because the missing item may
  be intentionally omitted or not applicable. This prevents frustration
  for businesses that can't fill every field.

## 9. Recommendation rules

Each failed check produces exactly one recommendation. Recommendations
are ordered by check number (1–10), which approximates structural
importance: switch → identity → location → contact → visual → precision
→ supplemental.

| Failed check     | Recommendation text                                                        |
|------------------|----------------------------------------------------------------------------|
| Schema output    | Enable structured data so search engines can find your business.           |
| Business name    | Add your business name.                                                    |
| Core address     | *(Specific — see Check 3 §5 for partial-fill variants)*                   |
| Address detail   | Add your state/province or postal code for a more precise address.         |
| Phone number     | Add your phone number.                                                     |
| Business logo    | Add a business logo.                                                       |
| Business photos  | Add at least one business photo.                                           |
| Map coordinates  | Add both latitude and longitude for your map location.                     |
| Social profiles  | Add at least one social media link.                                        |
| Price range      | Add your typical price range.                                              |

### Core address recommendation variants (Check 3)

| Missing fields        | Recommendation text                                    |
|-----------------------|--------------------------------------------------------|
| Only street_address   | Add your street address.                               |
| Only locality         | Add your city or town.                                 |
| Only country          | Add your country.                                      |
| Two or three missing  | Complete your address — add your street, city, and country. |

All recommendation strings are translatable via `__()`.

When all 10 checks pass, no recommendations are shown.

## 10. WooCommerce handling

`woocommerce_product_schema` and `woocommerce_currency` do **not** affect
the Schema Health score.

**Rationale:**
- The score measures LocalBusiness structured data completeness.
- Product schema is a separate concern (WooCommerce product pages).
- A non-WooCommerce business must never be penalised.
- Even when WooCommerce is active, product schema is opt-in and
  independent of the LocalBusiness setup quality.
- The JSON-LD builder uses WooCommerce settings only within a `Store`
  type + WooCommerce active conditional — they are not part of the core
  LocalBusiness graph.

## 11. Legacy fields

`legacy_aggregate_rating` and `legacy_review_count` are **not scored**.

**Rationale:**
- Migration-era fields carried forward for backward compatibility.
- Scoring them would encourage users to enter or maintain review/rating
  data, which is not the plugin's purpose.
- They are not exposed as regular settings fields in the UI.
- They should eventually be deprecated and removed.

## 12. Business type evaluation

`business_type` is **not scored**.

**Evaluation:**

The available types are `LocalBusiness` (default), `Restaurant`, `Hotel`,
`ProfessionalService`, and `Store`. More specific types can enable richer
Knowledge Panel features in Google search.

However:
- The default `LocalBusiness` IS valid, correct structured data.
- Many businesses (laundromats, repair shops, salons, gyms) are
  accurately described as generic local businesses.
- There is no check that can distinguish "user hasn't reviewed this" from
  "user correctly left the default."
- Penalising the correct default creates a nag that frustrates users who
  made the right choice.

**Decision:** Excluded from scoring. The field always produces valid
`@type` output regardless of which option is selected.

## 14. Edge cases

| Scenario                           | Behavior                                    |
|------------------------------------|---------------------------------------------|
| `images` is a string, not array    | Treat as empty array → check 7 fails        |
| `social_profiles` is a string      | Treat as empty array → check 9 fails        |
| `latitude = "0"`, `longitude = "0"`| Passes — (0, 0) is technically valid        |
| `latitude = "0.0"`, `lng = "0.0"`  | Passes — `is_numeric("0.0")` is true        |
| `phone = "+1 (555) 123-4567"`      | 10 digits → passes                          |
| `phone = "ext. 123"`              | 3 digits → fails                            |
| `business_name = "  AB  "`         | Trimmed = "AB" (length 2) → passes          |
| `business_name = " A "`            | Trimmed = "A" (length 1) → fails            |
| `logo = "HTTP://EXAMPLE.COM/X"`    | Starts with HTTP:// (case-insensitive) → passes |
| `price_range = " "`                | Trimmed = "" → fails                        |
| `price_range = "$"`                | Trimmed = "$" (non-empty) → passes          |
| `latitude = "90.0001"`             | > 90 → fails                               |
| `latitude = "-90"`, `lng = "180"`  | Both at boundary → passes                   |
| All WC fields set, all else empty  | Score 0/10 — WC fields excluded             |
| Legacy fields populated            | No effect — excluded                        |
| `images = ["", "", ""]`            | No element starts with http(s) → fails      |

## 15. Proposed class and API

### Location

```
src/Admin/HealthScore.php
```

Namespace: `AnkitRawat\LocalSEO\Admin`

### Class

```php
final class HealthScore {

    /**
     * Calculate the schema health score.
     *
     * @param array<string, mixed> $settings The plugin settings array
     *     (merged with defaults).
     * @return array{
     *     score: int,
     *     total: int,
     *     status: string,
     *     checks: list<array{id: string, label: string, passed: bool}>,
     *     recommendations: list<string>,
     * }
     */
    public static function calculate( array $settings ): array;
}
```

### Return value structure

```php
[
    'score'           => 7,              // int 0–10
    'total'           => 10,             // always 10
    'status'          => 'Almost there', // one of the 4 status labels
    'checks'          => [
        [ 'id' => 'schema_enabled',  'label' => '...', 'passed' => true  ],
        [ 'id' => 'business_name',   'label' => '...', 'passed' => true  ],
        [ 'id' => 'core_address',    'label' => '...', 'passed' => true  ],
        [ 'id' => 'address_detail',  'label' => '...', 'passed' => false ],
        [ 'id' => 'phone',           'label' => '...', 'passed' => true  ],
        [ 'id' => 'logo',            'label' => '...', 'passed' => true  ],
        [ 'id' => 'photos',          'label' => '...', 'passed' => false ],
        [ 'id' => 'coordinates',     'label' => '...', 'passed' => true  ],
        [ 'id' => 'social',          'label' => '...', 'passed' => true  ],
        [ 'id' => 'price_range',     'label' => '...', 'passed' => false ],
    ],
    'recommendations' => [
        'Add your state/province or postal code for a more precise address.',
        'Add at least one business photo.',
        'Add your typical price range.',
    ],
]
```

### Design notes

- **Static method:** No constructor state. Pure function of the settings
  array.
- **`$settings` parameter:** Accepts the array from
  `get_option( Plugin::OPTION, [] )` merged with `Settings::defaults()`.
  The caller passes it in — the class does not call `get_option()` itself.
  This makes it trivially testable without WordPress loaded.
- **All user-facing strings** (`label`, recommendation text, status) use
  `__()` with the plugin text domain for translation.
- **`total`** is always 10. Included so the UI doesn't hardcode the
  denominator.
- **Check order** in `checks` is always 1–10 (schema, name, core
  address, address detail, phone, logo, photos, coordinates, social,
  price range).
- **Recommendations** only include items for failed checks, in check
  order.

### Integration consideration

`HealthScore::calculate()` is a pure function. It takes an array and
returns an array. The only WordPress dependency is `__()` for
translations. Unit tests can define a stub `__()` that returns its first
argument unchanged.

## 17. Performance

- **No database queries.** Settings array passed in by caller.
- **No HTTP requests.** All checks are string/numeric operations.
- **No file I/O.** No remote image inspection or file reads.
- **No frontend impact.** Computed only in wp-admin on the settings page.
- **No JSON-LD impact.** Does not modify settings or schema output.
- **Computational cost:** 10 lightweight checks on scalar values and
  small arrays. Negligible — well under 1ms.

## 18. Privacy and security

- No user data is collected, transmitted, or logged.
- No external services are contacted.
- The score is computed locally from existing settings.
- Displayed only to users with `manage_options` capability.
- Compliant with WordPress.org plugin guidelines.
- No telemetry, tracking, or analytics.

## 19. Open decisions

### 19.1 — UI placement and design

Where and how the score is displayed on the settings page is deferred to
M4 implementation. The algorithm is UI-agnostic.

### 19.2 — Schema-disabled banner design

The exact visual design of the "structured data is disabled" notice is
deferred to M4 implementation.

### 19.3 — Future WooCommerce health indicator

If WooCommerce product schema gains its own health metric in a future
milestone, it should be a separate indicator clearly labelled as
WooCommerce-specific, not merged into this score.

### 19.4 — Coordinate (0, 0) handling

The specification currently treats (0, 0) as valid because it is a
technically valid coordinate. In practice, no local business exists at
Null Island (Gulf of Guinea). A future iteration could add a soft warning
("Are you sure your business is at 0°N, 0°E?") without affecting the
score. Deferred — not M4 scope.
